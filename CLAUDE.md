# CLAUDE.md

## Project Overview

Halmos Editor (Hermes in the code: the Go module, bundle id and data dir) is a desktop app built with **Wails v3 (beta)** — `v3.0.0-beta.30`, pinned identically across `go.mod`, the `wails3` CLI and `@wailsio/runtime`, which must be bumped together: a Go backend with a Svelte 5 + TypeScript + Vite frontend rendered in a native webview. The Go module is named `hermes`, so generated bindings live under `frontend/bindings/hermes`.

## Commands

Wails v3 uses [Task](https://taskfile.dev) for orchestration; `wails3 task <name>` and `task <name>` are equivalent. The root `Taskfile.yml` dispatches `build`/`package`/`run` to the platform-specific Taskfile in `build/<GOOS>/`.

- `wails3 task common:generate:bindings` — regenerate the TypeScript bindings in `frontend/bindings/`
- `go test ./. && go build -o /dev/null .` — run Go tests and verify build (use `.` not `./...`)
- `wails3 task package` — rebuild the distributable `bin/<app>.app` bundle. **`build` does not package.** `build` refreshes only the bare binary in `bin/`; the `.app` around it is stale until `package` runs, so copying that bundle anywhere ships whatever was last packaged. Same family of trap as the `run` one below.
- `wails3 task run` — build and launch the app. The `run` task in `build/darwin/Taskfile.yml` has `deps: [build]`, but that is a **hand edit to a generated file**: Wails' own template has no deps, so `run` only copied the existing `bin/Halmos Editor` into the `.dev.app` bundle, re-signed it and launched it — after editing source, it silently launched the previous binary. `update:build-assets` regenerates that Taskfile and will drop the line; re-add it, and until then use `wails3 task build && wails3 task run`. Either way, before reporting that a change works in the app, confirm the binary actually contains it (`strings "bin/Halmos Editor" | grep <a new symbol>`, or compare `ls -lT "bin/Halmos Editor"` against the source mtimes).
- Safari Web Inspector needs a dev build (`DEV=true`); see the `web-inspector` skill before profiling.

## Architecture

The core Go↔JS boundary works like this:

1. **Generated bindings**: `wails3 generate bindings` scans registered services and emits typed TS wrappers into `frontend/bindings/` (imported as `../bindings/hermes` in `App.svelte`). Never hand-edit these files — regenerate them after changing a service's API. The build tasks regenerate them automatically.
2. **Frontend pipeline** (editor and preview):
   - `lib/renderer.ts`: markdown-it + KaTeX plugin; renders markdown to HTML; intercepts `vega-lite` code blocks as chart placeholders; citations are parsed by `lib/citations.ts` (markdown-it rule + citeproc-js formatter), bibliography data comes from a frontmatter-named `.bib` read/watched through Go (`bib:changed`, emitted only when the content's hash changes) and parsed in a Web Worker by `lib/bibLoader.ts` (`bibWorker.ts`; last text cached, main-thread fallback; a reload with the same text and style keeps the formatter), and Zotero insertion uses BBT's CAYW via `PickCitations`. `lib/styleOptions.ts` applies the frontmatter's author-list keys (`citation-et-al-min`, …) to a copy of the style's XML before the formatter is built and before CSL is sent for export. `lib/toc.ts` (core rule after `source_line`) gives every heading a slug id and, when the frontmatter says `toc: true`, renders the contents list at the first `[[toc]]` paragraph or the top (`toc-depth` filters, default 3). `lib/frontmatter.ts` reads `title`, `author`, `date` and `abstract` with the `yaml` library (pinned at 2.9.1; a YAML error or unsupported shape drops only the metadata, and the six older keys keep the line parser), `lib/titleBlock.ts` renders the title block from them, and `lib/exportMetadata.ts`'s `authorsForExport` rewrites `author` in the copy sent to the portal as a list of text entries (`Name, Affiliation`); the document itself is never changed.
   - `lib/figures.ts`: a markdown-it core rule (`figurePlugin`) that decides what counts as a figure — a Vega-Lite `title` or an image's non-empty alt text is a caption, and a caption is what makes a figure — and numbers them in document order; captions render as `Figure 2: Caption` with a colon. A chart or diagram is matched by the first word of its fence info string (`fenceLanguage`), not the whole string, so ` ```vega-lite {#fig:name} ` is still a chart. It does the `<figure>`/`<figcaption>` token surgery itself for images; for a chart it only stamps the caption and number onto the fence token, since `renderer.ts`'s fence renderer already hand-builds that block's HTML and reads the stamp back out. It also owns the two document-wide settings' vocabulary (`ChartWidth`, `FigureAlignment`) and `cssTextAlign`, the sole place Hermes' own `centre` spelling is mapped to CSS's `center`.
   - Cross-references (`@fig:name`, `[@fig:a; @fig:b]`, `@Fig:name`; labels `{#fig:…}`, `{#tbl:…}`, `{#eq:…}`): `lib/crossrefs.ts` holds the vocabulary (kinds, `KIND_WORD`, `isCrossrefKey`, label slugs, where a label is appended to each kind of block). `lib/tableCaptions.ts` is a markdown-it rule that turns a `: Caption {#tbl:name}` line after a table into a numbered caption (tables number apart from figures; without it markdown-it reads the line as a paragraph). `lib/equations.ts` numbers only labelled top-level display maths (`$$ … $$ {#eq:name}`). `figures.ts`, `tableCaptions.ts` and `equations.ts` each stamp a `TargetMeta` on their token; `lib/crossrefTargets.ts` (`crossrefPlugin`, `collectTargets`) gathers those in document order, resolves each reference token from `citations.ts` (a key starting `fig:`/`tbl:`/`eq:`/`sec:` is never a citation; `@sec:` renders `Section ??`), writes `Figure 2` as a link to the target's id, and reports the misses (`Figure ??`) that the status bar counts. `lib/crossrefCompletion.ts` is the picker: `@fig:`/`@tbl:`/`@eq:` completion, the Insert → Cross-reference… list (`menu:insert-crossref`), and `planReference`, which returns the edits (reference plus the label written once on the target, `-2` if taken; a reference on the target's own line is refused). Only top-level numbered targets, plus top-level unlabelled equations, are `pickable`; `EquationName.svelte` asks for a short name for an unlabelled equation. `lib/exportCrossrefs.ts` (`labelForExport`) adds generated `fig:halmos-n`/`tbl:halmos-n` labels to unlabelled numbered targets in the copy sent to the portal for Word and LaTeX, so pandoc-crossref numbers as the preview does, and `abstractReferencesForExport` writes references in the frontmatter's `abstract` as plain text ("Figure 2"), since pandoc-crossref resolves only the body; the document is never changed. In LaTeX, charts and diagrams stay as code, so a reference to one does not resolve (Backlog).
   - `lib/charts.ts`: Vega-Embed integration; hydrates chart placeholders with live SVG charts; caches embedded specs for efficiency. `vega-embed` is imported dynamically (`await import('vega-embed')`), not statically, from both call sites — that is load-bearing for startup bundle size, so don't convert it to a static import.
   - `ChartBuilder.svelte`: the graphical chart editor opened from Insert → Chart… or the toolbar; pastes/imports a table via `lib/dataTable.ts` (delimited-text parsing and type inference) and encodes it with `lib/chartSpec.ts` (`buildSpec`/`readSpec`, the `BuilderState` <-> Vega-Lite JSON round trip). `App.svelte`'s `openChartBuilder`/`commitChart` decide insert-vs-replace from `Editor.svelte`'s `enclosingChartBlock`, and re-validate the target range against the live document at commit time before writing, since the modal does not block keyboard input to the editor behind it. `TableBuilder.svelte` follows the same open/commit shape for GFM tables — `Editor.svelte` passes `extensions: [Table]` from `@lezer/markdown` to `markdown()`, which is what makes `enclosingTable` possible; `lib/pipeTable.ts` parses and serialises (padded, with alignment; cells are raw markdown source); and `commitTable` re-validates the range by comparing the live text against what was captured when the builder opened, rather than by re-parsing it — the same guard `commitChart` applies before writing.
   - `lib/markdownCommands.ts`: editor formatting as pure CodeMirror `StateCommand`s, invoked from the Format menu via the `menu:format` event and guarded by `isProtected` so they never rewrite fenced code or frontmatter. Accelerators are owned by `menu.go`, because AppKit dispatches menu key equivalents before the webview sees them — *except* for chords CodeMirror's `defaultKeymap` already claims with `preventDefault` (⌘I is `selectParentSyntax`, ⌘⇧K is `deleteLine`). The webview wins those, so `Editor.svelte` re-binds them at `Prec.highest` and routes them back through App's `applyFormat`. Check `defaultKeymap` *and* `foldKeymap` before adding an accelerator — `foldKeymap` claims ⌘⌥[ and ⌘⌥] for folding, which the View menu reflects rather than re-binds, since the keystroke already does what the menu item says.
3. **Events (Go → JS)**: Go emits events with `app.Event.Emit(name, data)`; the frontend subscribes with `Events.On(name, cb)` from `@wailsio/runtime`. Hermes emits `menu:new`, `menu:open`, `menu:open-recent` (path payload), `menu:insert-citation`, `menu:insert-crossref` (payloadless — the editor opens its cross-reference list at the cursor), `menu:insert-chart`, `menu:insert-table` and `menu:insert-code` (a language token, `""` for Plain text) (from the Insert menu), `menu:save`, `menu:save-as`, `menu:export-pdf` (payloadless — the frontend calls `ExportPDF` with the document's path), `menu:export-html` (payloadless — the page is built from the rendered preview, which only the frontend holds; Go only shows the save panel, reads local images as data URIs and writes the file), `menu:export-pandoc` (`"docx"` or `"latex"`), `menu:account` (payloadless, from the app menu's Account…), `menu:check-updates` (payloadless — the frontend owns the dialog and toast that report the result), `menu:command-palette` (payloadless, from View → Command Palette… on ⇧⌘P, through `docEmit`; every menu item is registered with `commandSet.item` in `commands.go`, and the palette lists and runs those same actions through `CommandService`), `menu:citation-style` (a bundled or installed style id, or `"find"` for Find a Style…, whose Choose a file… opens the `.csl` panel), `menu:format`, `menu:fold` and `menu:find` (all command-name payloads; `menu:find` drives `Editor.find`, because the native Find roles search WKWebView's page text, not the CodeMirror document) from `menu.go`; `close:confirm` (payload `"close"` from the window's close button, `"quit"` from ⌘Q in `menu.go`, and from the Dock's Quit, logout and restart via `ShouldQuit` in `main.go` — `DocumentService.Quit` marks the quit approved so it is not asked again; Go sends it when the document is dirty **or** a chart/table builder is open — `SetBuilderOpen`, `mustAsk` — and the frontend asks "Discard the chart?" before the unsaved-changes dialog), `document:closed` (payloadless — the window was hidden, not destroyed, so the app stays in the Dock), `file:open` (path payload — a `.md` handed over by Finder while running; one that arrives at cold launch is buffered by `launchfiles.go` and collected with `TakeLaunchFile`), `recents:changed`, and `settings:changed` from `main.go`; `bib:changed` from the bibliography watcher; `portal:pairing` (`{state, email?, error?}`: approved, denied, expired or failed) from `portalservice.go`; and `document:changed` (`{path, version, content}` — the open file's text was changed by another program), `document:moved` (`{from, to}`) and `document:deleted` (`{path}`) from the document watcher. These are plain, untyped events — there is no `application.RegisterEvent[T](name)` registration step in `main.go` (or anywhere else), so the frontend types each payload manually where it calls `Events.On`.

Other things to know:

- **Editing the long prose documents** — `ROADMAP.md` (700+ lines), `README.md`, `CHANGELOG.md`. Scripted edits that splice by string index have corrupted `ROADMAP.md` twice, both times pushed before anyone noticed. The failure is always the same shape: `start = s.index(a)` and `end = s.index(b)` where `b` occurs *earlier* in the file than `a`, so `s[:start] + new + s[end:]` emits everything between them twice. Ticking a roadmap item is exactly this pattern, because the replacement text and the surrounding entries look similar. So: assert the boundaries are ordered (`assert end > start`) before splicing, prefer replacing one unique block with `str.replace` and `assert s.count(old) == 1` over index arithmetic, and check the shape afterwards — `grep -c '^- \['` before and after should differ by exactly what you intended, and `grep '^## '` should be unchanged. The same care applies to any regeneration: verify the region you are about to overwrite, not just the result.
- `ROADMAP.md` release sections from v1.0.0 on open with `Serves: Mx.y`, naming the milestone in the Halmos product roadmap (`../ROADMAP.md`, kept outside this public repository). Product direction, payment and legal work live there; this file lists the editor's own work. When you tick or move an item here, update its milestone row there and run `../bin/check-roadmaps`.
- The licence texts are copied into `Contents/Resources/licences` by `bundle:licences` in the **root** `Taskfile.yml`, which the root `package` task runs after the platform one. A distributed binary has to carry them: Apache-2.0 §4(d) requires `NOTICE` to travel with the work, and citeproc-js is dual CPAL/AGPL, both of which require their licence to accompany the distribution — having them in the repository covers source distribution only. It lives in the root Taskfile because `build/<GOOS>/Taskfile.yml` is regenerated by `update:build-assets` and the root one is not. The task **re-signs afterwards**, because `codesign` seals `Contents/Resources` and files added later invalidate the signature — with the Developer ID when the keychain has one, ad-hoc otherwise, because macOS binds privacy grants such as Screen Recording to the signature and an ad-hoc one changes every build (see the `demo-mode` skill).
- The Quick Look extension is `quicklook/`: a view-based `QLPreviewingController` (`PreviewViewController.swift`, pure helpers in `PreviewText.swift`, tested by `quicklook/Tests/main.swift` via `wails3 task quicklook:test`) that Finder uses for the space-bar preview of `.md` files. It reads the file itself (first 5 MB, invalid UTF-8 replaced), loads `frontend/quicklook.html` + `src/quicklook.ts` from its own `Resources/quicklook` in a WKWebView, and calls `window.renderMarkdown(text, info)`, which resolves after hydration or 5 s; Swift has a 10 s backstop. The page is built separately by `vite build --mode quicklook` into `frontend/dist-quicklook` as one classic IIFE script, because a `file://` page cannot load module scripts; it must never import the Wails runtime or bindings. Packaging now needs `swiftc` (Xcode or the Command Line Tools): `quicklook:build` compiles it universal, and `quicklook:embed` copies it into `Contents/PlugIns` and signs it with its own sandbox entitlements **before** the outer app is signed — in both `bundle:licences` and `release`, and never with `--deep`, which would not apply those entitlements. `release` deletes `bin/HalmosQuickLook.appex` first so it is always rebuilt. Limits, by design: no `.bib` or citation formatting (keys show raw), no document-relative or remote images (shown as `[Image: name]`; only inline `data:image/` images render), light theme on A4 only. The appex **must** have `com.apple.security.network.client`: without it the sandbox kills WKWebView's web content process the moment the page loads (no `didFail`, just `webViewWebContentProcessDidTerminate`), and Quick Look silently falls back after the 10 s backstop — which looks like a slow preview, not a broken one. "Fetches nothing" is enforced instead by `PreviewText.offlineRules`, a content rule list blocking every non-`file:`/`data:`/`about:`/`blob:` URL, installed before the page loads; the page is not loaded if it cannot be installed.
- Opening a local path from Go uses `app.Browser.OpenFile(path)`, never `OpenURL("file://"+path)` — the bundle name contains a space, so a hand-built file URL is malformed. Both end at `exec.Command("open", target)`, and the implementation discards the result in a goroutine, so **a bad target fails silently**: only a failure to start `open` is returned. Budget for that when debugging anything that opens a file or URL.
- The application is named **Halmos Editor** — `APP_NAME` in the root `Taskfile.yml`, which names the bundle (`bin/Halmos Editor.app`), the binary inside it, and `CFBundleExecutable`. macOS names an app by its bundle filename, so `CFBundleName` alone was not enough: the bundle read as "hermes" in Finder and the Dock while the plist said otherwise. The space means paths must be quoted — the macOS build, package and run tasks already quote every use, but the docker and server tasks in `build/Taskfile.yml` do not, so they would need quoting before they are used.
- The product was renamed from Hermes Editor to Halmos Editor in 0.13.0, user-facing only. The bundle id `com.qxquantum.hermes`, the `hermes/` data dir, the Go module, `/_hermes/image` and `HERMES_DEMO` keep the old name on purpose: TCC grants, the `.md` handler, preferences and unsaved recovery drafts are all keyed to them, and renaming any of them strands an existing user's data.
- **Never create a repository named `richarc/hermes`.** The repo was renamed to `richarc/halmos`, and GitHub redirects the old name only while nothing else holds it. Every ≤0.12 install polls `raw.githubusercontent.com/richarc/hermes/main/updates/latest.json`; a new repo at that name ends the redirect and those users never hear of another update.
- App metadata (name, version, product identifier) lives in `build/config.yml`; after changing it, run `wails3 task common:update:build-assets` to regenerate build assets (this overwrites manual edits to those assets).
- The app icon pipeline (layered Icon Composer icon, `Assets.car`, `CFBundleIconName`, `appicon.png`) is documented in the `app-icon` skill; read it before touching icons, `Info.plist` icon keys, or `update:build-assets` after removing `Assets.car`.
- Persisted preferences all live in the single `Settings` struct in `settings.go`, behind the `Settings`/`UpdateSettings` binding pair. Adding one is a field with a `json` tag, a default in `defaultSettings`, and a clamp in `normalise`; persistence, the `settings:changed` event, the menu rebuild, and the TS model all follow with no extra wiring. `settingsStore` reads the file once and writes only on a real change, so don't reach for the file directly.
- The document watcher is `docwatch.go` with `docstate.go` (the tracked document) and `docpath_darwin.go`. It polls the open file every 1 s and acts only after two equal stats (the settle rule). Halmos's own saves never trigger it: `Save` re-tracks the new version under `docMu` before the next poll can see the file. The version is a SHA-256 of the content, not an mtime. A move is followed with `fcntl(F_GETPATH)` on a held-open file, which is darwin-only; a move into `/.Trash/` or another volume's `/.Trashes/` counts as a delete, and a file that reappears after a delete is always a change. `Save(path, content, overwrite)` returns `SaveResult{Conflict}` instead of overwriting an external change.
- Recovery drafts are `recovery.go` (a `draftStore` under `<data>/hermes/drafts/`, keyed by a hash of the document path, `untitled` for none) behind `WriteDraft`/`DiscardDraft`/`RecoverDraft`, and `lib/recoveryDraft.ts` decides *when*: debounced 2 s while dirty and `autoSave` is on, discarded on the dirty-to-clean transition, both through one ordered queue so a discard cannot overtake a write in flight. `App.svelte` awaits `settle()` before quitting for the same reason. Go decides whether a draft is still worth offering (`find`: a draft carries `base` (the version hash of the disk text its edits started from) and `saved` (the version hash Halmos last saved over its path), and is dropped only when the file now holds the draft's text or Halmos saved over it; `Draft.changed` is set when another program wrote the file; legacy drafts without these keep the old mtime rule; a draft follows a moved document; `draftStore.mu` serialises its file I/O) — keep that rule in Go, so the frontend never compares files. A draft is never written over the document; explicit Save remains the act of record.
- The update check is `update.go`: `CheckForUpdates(force)` GETs the bare feed URL (`updates/latest.json` on `main`, via raw.githubusercontent.com) with no query string and no custom header, at most once per 24 h through a timestamp in `<data>/hermes/update-check.json` written before the fetch, validates the version as `MAJOR.MINOR.PATCH`, and **derives** the release URL from it — the feed is never trusted for a destination. `force` (Help → Check for Updates…) skips both the setting gate and the throttle. The feed, the release guard in `Taskfile.yml`, and the push-last ordering in README's release steps are one contract: bump `config.yml` and the feed together, publish, then push. The three-state `updateCheck` setting is asked about once at first launch in `App.svelte`, after the recovery-draft offer and never over it.
- Spell checking is native WebKit, scoped by attribute: `lib/spellcheck.ts` sets `spellcheck="true"` on the content element and wraps `protectedRanges` (code/URL/HTML from the syntax tree, frontmatter by line, maths and citations by pattern) in `spellcheck="false"` marks, which WebKit honours per element. `Editor.svelte` holds it in the editor's only `Compartment`, driven by the `spellcheck` prop from the `SpellCheck` setting. WebKit's continuous-checking flag has no registered default in a WKWebView app, so `spellcheck_darwin.go` registers `WebContinuousSpellCheckingEnabled` on before the window exists; do not move that call after `application.New`. Coverage is WebKit's: it checks the word typed and the word the caret leaves, never a loaded document — see the roadmap item before treating "no underlines on open" as a bug. `autocorrect` stays off.
- `print_darwin.go` has two routes, and their rules differ. **Export PDF…** (`hermesExportWebViewPDF`) shows no panel: it builds the print info from the Paper Size setting and renders straight to the file. Set `paperName` **before** `paperSize` (setting the name resets the size to a rounded catalogue figure), turn vertical and horizontal centring **off** (both default to YES and inherit the last print job's values, which centres a short last page), and keep the margins **zero**: the CSS `@page` rule from `lib/paper.ts`'s `pageRule` supplies them, and NSPrintInfo margins crop rather than add. WebKit ignores the `@page` top margin, which is why `paper.ts` keeps 25mm on the margins across the short edge and scales the other pair to the paper's shape. **File → Print…** (`hermesPrintWebView`) runs `NSPrintPanel` **before** creating the `NSPrintOperation`, and that ordering is load-bearing. Creating the operation first — which is what Wails' own implementation does — makes `WKPrintingView` paginate against the print info supplied at that moment; the panel then substitutes the chosen printer's paper size and imageable area, the content reflows, and the operation still renders only the pages it originally counted, silently dropping the tail of a long document. The cost is that the panel has no live preview, since the preview is drawn by the operation; `NSPrintPanelShowsPreview` on a standalone panel does nothing. Both routes use `runOperationModalForWindow:`, never `[po runOperation]`, which deadlocks on the main thread — `WKPrintingView` needs the runloop to service the web content process. The frontmatter's `header`/`footer` (`lib/pageFurniture.ts` → `PageFurniture`) are drawn **after** WebKit renders, because WebKit has no CSS page-margin boxes: with either set, Export PDF prints to a temporary file and `HermesExportFinisher` (the operation's didRun callback) has `pdfstamp_darwin.go` draw them on each page with a `PDFPage` subclass, writing to the chosen path; if that fails the unstamped PDF is moved there. Placeholders are filled in one pass there, and `{date}` is formatted there too, because the webview's locale does not follow the Mac's region.
- `portalservice.go` (`PortalService`) is the editor's side of the Halmos portal: pairing this Mac to an account by device flow (`StartPairing`, `CancelPairing`, `SignOut`, with the result as `portal:pairing`), reading the account (`Account`), and Word/LaTeX export through the portal's Pandoc. `Export` sends the frontend's `ConvertRequest` as `convertBody`, the contract's shape: the `PageFurniture` Export PDF uses becomes `page_furniture`, with `{date}` from `localLongDate` (`localdate_darwin.go`). `portalclient.go` makes the HTTP calls. Tokens and device codes stay in Go; the frontend sees only what it shows.
- Citation styles from the CSL repository are `styleservice.go` (`StyleService`, Find a Style…), over `styleclient.go` (the portal's public `/styles/index.json` and `/styles/<id>.csl`; same-origin redirects only, each file checked against the index's SHA-256 and for a `<style>` root) and `stylelibrary.go` (`<data>/hermes/styles/`, one lock across each `library.json` read-merge-write: `<id>.csl`, `library.json`, the cached index with its ETag, revalidated after an hour; search and ranking run here, so the 3.6 MB index never reaches the webview). Every `csl:` value that is not bundled goes through `ResolveStyle`, which returns the XML that formats: a style file, an installed style, or one fetched and installed from the repository — the last only with `fetch`, which `reloadBibliography` sets only after the `csl:` value has stood unchanged for a second, so typing an id installs nothing on the way; a dependent style (a journal's name pointing at a parent) always resolves to its parent's XML, because citeproc formats nothing with a dependent style. Installs write files first and `library.json` last. `onChanged` rebuilds the menu, which lists installed styles the author chose (not those installed only as a parent).
- Images stored beside the document are served by `localimages.go`, registered as `AssetOptions.Middleware` in `main.go`. It serves images only: `localImageFile` requires an `imageTypes` extension on both the name asked for and the file a symlink leads to, and the response carries a fixed `Content-Type`, `nosniff` and a `sandbox` CSP. A document can come from anyone, and `..` and absolute paths are allowed, so without that check a document could name any file on disk. The HTML and Word export readers go through the same function. The webview loads the embedded bundle, so a document-relative `<img src>` would resolve against *that* and 404 — `renderer.ts`'s image rule rewrites a local source onto `/_hermes/image?doc=…&src=…` and Go joins the pair with `resolveAgainstDoc`, the same package-level resolver `ReadBibliography` uses. Keep `LOCAL_IMAGE_ROUTE` in `renderer.ts` and `localImageRoute` in `localimages.go` in step. markdown-it percent-encodes link destinations before a renderer sees them, so the source is decoded before being re-encoded for the query string; skipping that sends `%2520` and looks for a file with a literal `%20` in its name.
- Links in the preview are intercepted by a delegated click handler in `Preview.svelte` and opened in the system browser via `Browser.OpenURL` from `@wailsio/runtime`; a plain `<a href>` click would otherwise navigate the webview away and destroy the app state.
- Colours live in one place: the custom-property palette at the top of `frontend/public/style.css`, with a `:root[data-theme="dark"]` block that must define exactly the same names. `src/lib/styleContract.test.ts` fails the build if a rule uses a literal colour or if the two blocks diverge. CodeMirror is themed through the same variables (`Editor.svelte`), so switching needs no reconfiguration. The dark `--bg` is duplicated in `main.go` as the window background because Go cannot read the CSS.
- Demo mode (`HERMES_DEMO=<script>`, `demo.go`, `lib/demo.ts`, `docs/demos/`) is documented in the `demo-mode` skill.
- Figure alignment is one attribute, not a class per element: `Preview.svelte` writes `data-figure-align` (`"left"`/`"center"`/`"right"`, via `cssTextAlign`) onto the preview root, and `style.css` matches `[data-figure-align="…"] figure`/`.vega-lite-chart`/`p:has(> img:only-child)`/`p:has(> a:only-child > img:only-child)` off it — the last two are how an uncaptioned (or linked) bare image gets aligned, since it never becomes a `<figure>` at all. Renaming the attribute or its values needs both sides updated together.
